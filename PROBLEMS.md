# Реестр функциональных проблем Larix Nexus Desktop

## Область аудита

Этот реестр составлен по содержимому переданного проекта и ориентирован на:

- корректность синхронизации local ↔ cloud;
- сохранность пользовательского состояния;
- скачивание и сохранение файлов;
- обработку сетевых ошибок;
- понятность результата операций для пользователя;
- воспроизводимость сборки и тестов.

**Не входят в область этого аудита:** `telegram_bot/**`, управление секретами, TLS и другие вопросы безопасности. Они намеренно не учитывались при приоритизации.

## Метаданные

- **Дата аудита:** 2026-07-29
- **Источник:** архив проекта без каталога `.git`
- **Ветка и commit:** определить невозможно
- **Проверено:** 79 Python-файлов; основные потоки API, синхронизации, скачивания, workspace, уведомлений и локального состояния
- **Разрешённые изменения:** исходный код не изменялся; обновлён только этот реестр
- **Ограничения:** приложение с реальным Larix API и GUI PySide6 не запускалось; зависимости в архиве не описаны и в среде отсутствуют

## Карточки проблем

### ISSUE-001: Неполный ответ облака может быть принят за удаление файла

**Статус:** Исправлено
**Приоритет:** Critical  
**Уверенность:** Высокая  
**Область:** двусторонняя синхронизация  
**Рекомендуемый маршрут:** Terra Medium → Executor  
**Ожидаемый объём:** несколько связанных функций

#### Сценарий

В облаке существуют `a.txt` и `b.txt`. Во время синхронизации список папки получен, но запрос подробностей для `a.txt` временно завершился ошибкой. Подробности `b.txt` получены нормально.

#### Текущее поведение

`get_cloud_files()` просто не добавляет `a.txt` в результат. `compare_and_plan_sync()` видит файл в предыдущем состоянии и локально, но не видит его в текущем cloud-слепке и планирует `delete_local`.

Защита от пустого облака не помогает: она срабатывает только когда не получено ни одного обычного облачного файла. При частичном ответе удаление отдельного файла остаётся допустимым.

#### Затронутый код

- `larix_nexus/sync/engine.py:183-214` — пропуск файла при ошибке `get_document_details()`
- `larix_nexus/sync/engine.py:390-396` — защита только от полностью пустого ответа
- `larix_nexus/sync/engine.py:431-444` — планирование `delete_local`
- `larix_nexus/sync/engine.py:1313-1320` — результат scan не содержит признака полноты

#### Доказательство

Безопасный вызов `compare_and_plan_sync()` со старым состоянием из двух файлов, локальными двумя файлами и облачным результатом только для одного файла сформировал:

```text
[{'action': 'delete_local', 'path': 'a.txt', 'is_folder': 'false'}]
```

#### Возможное решение

1. Возвращать из cloud scan не только файлы, но и статус полноты: `ok`, `partial`, `failed`, список ошибок и неразрешённых ID.
2. Не трактовать отсутствие элемента как удаление, если scan неполный.
3. Запрещать destructive-операции и сохранение нового snapshot при `partial/failed`.
4. Для элемента, чьи details не получены, использовать безопасные метаданные из tree/listing только для сохранения присутствия либо переносить его из старого состояния как `unverified`.
5. Показывать пользователю, что синхронизация не завершена из-за неполного ответа сервера.
6. Добавить тест: один details-запрос падает, остальные проходят — локальных и облачных удалений быть не должно.

#### Критерии готовности

- Частичный cloud scan не создаёт `delete_local`/`delete_cloud`.
- При неполном scan старый snapshot не заменяется неполным.
- Повторная успешная синхронизация корректно обрабатывает файл.
- Ошибка видна в результате синхронизации, а не маскируется как успех.

#### Контекст для следующей модели

> **Передать:** Terra Medium  
> Проверь ISSUE-001 по текущему коду. Исследуй только `get_cloud_files`, `compare_and_plan_sync`, `sync_files_new` и связанные тесты. Не меняй код. Определи минимальный контракт результата cloud scan, который различает полный, частичный и неуспешный ответ. Подготовь точное ТЗ Executor: какие сигнатуры и вызовы изменить, как запретить destructive-операции и запись snapshot при неполном scan, как сохранить обратную совместимость и какие тесты добавить. Не расширяй задачу на общий рефакторинг sync engine.

### ISSUE-002: Отмена синхронизации сохраняет состояние и затем падает

**Статус:** Исправлено
**Приоритет:** High
**Уверенность:** Высокая  
**Область:** отмена синхронизации  
**Рекомендуемый маршрут:** Executor  
**Ожидаемый объём:** локальный

#### Текущее поведение

`execute_sync_operations()` при отмене возвращает wrapper:

```python
{"success": False, "cancelled": True, "stats": {...}, "errors": [...]}
```

При обычном завершении функция возвращает непосредственно `stats`. `sync_files_new()` всегда считает результат непосредственным `stats`, продолжает пересканирование и сохранение state, а затем обращается к `stats['downloaded']`.

#### Затронутый код

- `larix_nexus/sync/engine.py:907-910`
- `larix_nexus/sync/engine.py:932-935`
- `larix_nexus/sync/engine.py:1373-1383`
- `larix_nexus/sync/engine.py:1385-1496`

#### Доказательство

Контролируемый probe, где executor вернул cancellation-wrapper, показал:

```text
CANCEL_EXCEPTION = KeyError 'downloaded'
STATE_SAVE_CALLS = 1
```

То есть после отмены была попытка сохранить новое состояние, затем функция упала.

#### Возможное решение

1. Сделать единый контракт результата `execute_sync_operations()`.
2. Предпочтительный минимальный вариант: всегда возвращать один `stats`, содержащий `cancelled: bool`.
3. В `sync_files_new()` сразу после executor проверять отмену и возвращать штатный cancellation-result.
4. При отмене не выполнять post-scan и не сохранять новый snapshot.
5. Сохранить статистику уже завершённых операций только для отображения пользователю.
6. Добавить интеграционный тест отмены через `sync_files_new()`, а не только тест executor отдельно.

#### Критерии готовности

- Отмена не приводит к исключению.
- State после отмены не продвигается.
- UI получает `cancelled=True` и корректную частичную статистику.
- Следующий запуск повторяет незавершённые операции.

#### Контекст для следующей модели

> **Передать:** Executor  
> Исправь ISSUE-002 минимально. Унифицируй контракт `execute_sync_operations()` и обработку результата в `sync_files_new()`. При отмене немедленно заверши верхний уровень, не выполняй rescan/save state, не допускай `KeyError`. Сохрани частичную статистику для UI. Добавь тест, вызывающий `sync_files_new()` с отменой во время выполнения, и проверь, что `save_sync_state` не вызывается.

### ISSUE-003: Неудачное удаление в облаке засчитывается как успешное

**Статус:** Исправлено
**Приоритет:** High  
**Уверенность:** Высокая  
**Область:** sync delete cloud  
**Рекомендуемый маршрут:** Executor  
**Ожидаемый объём:** локальный

#### Текущее поведение

`APIClient.delete_document()` и `delete_folder()` возвращают `False` при отказе API. Sync executor игнорирует возвращаемое значение и всегда увеличивает `deleted_cloud`, если исключения не было.

#### Затронутый код

- `larix_nexus/sync/engine.py:1188-1206`
- `larix_nexus/api/client.py:2748-2801`
- `larix_nexus/api/client.py:2803-2824`

#### Последствия

Пользователь получает успешную статистику, failed path не попадает в retry-массив, а новый snapshot может скрыть незавершённое удаление. На следующем цикле файл может появиться снова или интерпретироваться неверно.

#### Возможное решение

- Проверять точное возвращаемое значение API.
- Только `True` считать удалением.
- `False` добавлять в `errors` и `failed_deletes_cloud`.
- Не удалять такой элемент из state.
- Добавить тесты отдельно для файла и папки при `False` и при исключении.

#### Контекст для следующей модели

> **Передать:** Executor  
> Исправь ISSUE-003 в `execute_sync_operations()`. Результат `delete_document/delete_folder` должен проверяться. `False` — это неуспешная операция с записью в `errors` и `failed_deletes_cloud`; счётчик `deleted_cloud` не увеличивать. Добавь тесты для file/folder, `True`, `False` и exception. Не рефактори остальные операции.

### ISSUE-004: Ошибки сохранения mappings и sync-state игнорируются

**Статус:** Исправлено
**Приоритет:** High  
**Уверенность:** Высокая  
**Область:** persistence синхронизации  
**Рекомендуемый маршрут:** Terra Medium → Executor  
**Ожидаемый объём:** несколько функций

#### Текущее поведение

`save_sync_mappings()` и `save_sync_state()` возвращают `bool`. Вызывающий код не проверяет его:

- `_save()` пишет «успешно» и запускает purge даже после `False`;
- `sync_files_new()` пишет «State saved» после `False`.

#### Затронутый код

- `larix_nexus/sync/manager.py:973-994`
- `larix_nexus/sync/state.py:102-125`
- `larix_nexus/sync/engine.py:1478-1491`

#### Последствия

UI и логи сообщают об успехе, хотя настройки или snapshot не сохранены. После перезапуска mapping может исчезнуть, а следующая синхронизация стартует с устаревшим состоянием. Purge после неудачного save дополнительно увеличивает риск потери служебных state-файлов.

#### Возможное решение

1. Сделать `_save()` возвращающим `bool` или выбрасывающим типизированную ошибку.
2. Не вызывать purge, если mapping не сохранён.
3. Проверять результат `save_sync_state()` и возвращать синхронизацию как failed.
4. Не показывать пользователю окончательный успех, если persistence failed.
5. Добавить тесты с monkeypatch `atomic_write_json -> False`.

#### Контекст для следующей модели

> **Передать:** Terra Medium  
> Проверь ISSUE-004 и подготовь минимальное ТЗ. Определи единый контракт сохранения mappings/state: bool или exception, и как ошибка должна доходить до UI/worker без большого рефакторинга. Обязательно запрети purge после неуспешного save и успешное завершение sync после неуспешной записи snapshot. Укажи конкретные тесты с отказом atomic backend.

### ISSUE-005: Повреждённый mappings-файл может привести к удалению sync-state

**Статус:** Исправлено
**Приоритет:** High  
**Уверенность:** Высокая  
**Область:** запуск менеджера синхронизации  
**Рекомендуемый маршрут:** Terra Medium → Executor  
**Ожидаемый объём:** несколько функций

#### Текущее поведение

При ошибке JSON/lock `load_sync_mappings()` в итоге может вернуть default с пустым `mappings`. `_load()` очищает `self.map`. Сразу после загрузки конструктор вызывает `_purge_stale_sync_artifacts()`, который считает все state-файлы orphan и удаляет их.

#### Затронутый код

- `larix_nexus/sync/manager.py:100-140`
- `larix_nexus/sync/manager.py:168-187`
- `larix_nexus/sync/manager.py:926-971`
- `larix_nexus/sync/manager.py:996-1006`
- `larix_nexus/sync/state.py:207-265`

#### Последствия

Одна временная ошибка чтения или повреждение `mappings.json` может не только скрыть настройки синхронизации, но и удалить snapshots всех ранее настроенных папок. Восстановить корректное направление изменений на следующем запуске становится сложнее.

#### Возможное решение

- Различать состояния `loaded`, `missing`, `invalid`, `locked/error`.
- Purge разрешать только после подтверждённой успешной загрузки валидного mappings-файла либо после явного пользовательского удаления mapping.
- Повреждённый файл не перезаписывать автоматически; сохранить/переименовать его для восстановления.
- Показать пользователю ошибку конфигурации с вариантом повторить чтение.
- Добавить тест: invalid mappings + существующие state-файлы — state остаются нетронутыми.

#### Контекст для следующей модели

> **Передать:** Terra Medium  
> Исследуй только загрузку mappings и purge state. Подготовь ТЗ, которое вводит явный статус загрузки и запрещает purge при invalid/locked/read-error. Missing-файл при первом запуске должен оставаться нормальным сценарием. Не менять формат mappings без необходимости. Добавь тесты для valid, missing, invalid JSON, lock timeout и явного удаления mapping.

### ISSUE-006: Обычное скачивание оставляет частичный файл под финальным именем

**Статус:** Исправлено
**Приоритет:** High  
**Уверенность:** Высокая  
**Область:** пользовательское скачивание  
**Рекомендуемый маршрут:** Executor  
**Ожидаемый объём:** локальный

#### Текущее поведение

`APIClient.download_file()` открывает конечный путь через `wb` до завершения сети. При обрыве возвращается пустая строка, но частичный файл остаётся. Существующий файл с тем же именем предварительно обнуляется.

#### Затронутый код

- `larix_nexus/api/client.py:1965-2015`
- `larix_nexus/ui/download_operations.py:25-80`

#### Доказательство

При тестовом ответе из 8 байт, который отдал 4 байта и оборвал соединение:

```text
result = ''
final file exists = True
size = 4
```

#### Возможное решение

- Скачивать в уникальный `.part` рядом с целевым файлом.
- Проверять `Content-Length`, если он предоставлен.
- После полного успеха выполнять `os.replace()`.
- При ошибке удалять только временный файл и сохранять прежний конечный файл.
- Прогресс считать независимо от наличия total.
- Добавить тесты: обрыв после chunk, mismatch размера, успешная замена, сохранение старого файла.

#### Контекст для следующей модели

> **Передать:** Executor  
> Исправь `APIClient.download_file()` по ISSUE-006: temp/part + atomic replace, очистка part при ошибке, сохранение существующего destination, необязательная проверка Content-Length. Не меняй публичный return-контракт: полный путь при успехе, пустая строка при неуспехе. Добавь сетевые unit-тесты.

### ISSUE-007: ZIP и папки могут сохраняться неполными с сообщением об успехе

**Статус:** Исправлено
**Приоритет:** High  
**Уверенность:** Высокая  
**Область:** скачивание папок, нескольких файлов и ZIP  
**Рекомендуемый маршрут:** Terra Medium → Executor  
**Ожидаемый объём:** несколько UI-функций

#### Текущее поведение

- `_zip_folder_into()` игнорирует `False` от `write_file_to()` и исключения.
- `_copy_folder_into()` игнорирует failed download/copy.
- Batch ZIP пропускает файлы с `ensure_downloaded() == ''`.
- Внешние обработчики после этого показывают «ZIP создан» или «Копирование завершено».

#### Затронутый код

- `larix_nexus/ui/download_operations.py:341-440`
- `larix_nexus/ui/main_window.py:5670-5733`
- `larix_nexus/ui/main_window.py:5736-5831`

#### Доказательство

При `write_file_to() -> False` архив был создан без исключения и содержал:

```text
F/a.txt — 0 bytes
```

#### Последствия

Пользователь получает внешне корректный ZIP или каталог, но часть файлов отсутствует либо имеет нулевой размер. Интерфейс не сообщает, какие файлы не удалось получить.

#### Возможное решение

1. Рекурсивные функции должны возвращать агрегированный result: total/succeeded/failed/errors.
2. Не создавать ZIP entry до подтверждения успешного скачивания либо писать через temporary file/buffer.
3. При failed items показывать «завершено частично» с количеством и списком/логом.
4. Полностью пустой или неуспешный ZIP удалить.
5. Для plain-копирования не скрывать ошибки `copyfile`.
6. Унифицировать повторяющиеся ветки скачивания в пределах задачи, но без широкого UI-рефакторинга.

### ISSUE-012: Активный файловый lock принудительно удаляется по таймауту

**Статус:** Подтверждено  
**Приоритет:** High  
**Уверенность:** Высокая  
**Область:** настройки, mappings, sync-state, уведомления  
**Рекомендуемый маршрут:** Terra Medium → Executor  
**Ожидаемый объём:** общий utility + дубликат

#### Текущее поведение

После истечения timeout `_acquire_file_lock()` удаляет существующий `.lock` без проверки владельца, PID, времени жизни процесса или уникального токена, затем захватывает путь сам.

- `larix_nexus/notifications/manager.py:105-125` — дублированная реализация

- Устранить дубликат реализации в notifications.

#### Контекст для следующей модели

### ISSUE-013: Папки с разными mtime повторно считаются загруженными

**Статус:** Подтверждено

- Для папки, существующей с обеих сторон, обычно планировать `noop`.
